# Nect legacy → Desktop requirements crosswalk (bounded first pass)

## Bottom line

The available evidence does **not** support saying that all old Nect requirements were carried over. The 2026-10-16 Desktop Brief selects a practical offline Windows editor and a named set of Musts, while explicitly preserving the C++/Qt Mission and keeping the legacy and Desktop formats distinct. The legacy product-direction document also cautions that its accepted direction does not pull the whole roadmap into a milestone. This is a bounded traceability pass over major requirement areas, not a full audit of every Notion requirement or every implementation/test.

### P0 — representative end-to-end acceptance target

The user-selected production target is one complete, re-editable identity-design task: create a mark with holes and live mixed Japanese/Latin text; refine curves and character spacing; make purpose-specific variants on the supported output frames; export SVG and raster; save the editable Nect project, restart, reopen, then edit the text and the original Boolean source again. Run the same supported semantic edits once through ordinary UI controls and once through the AI/machine-facing command surface. Their authored state and one-step Undo/Redo results must agree. Undo must restore the previous state without flattening the original mark or converting the live text to outlines.

Use the supported Desktop model and formats for this acceptance target: editable JSON remains the Nect project authority; SVG/PNG are output artifacts. Purpose-specific variants can use the current Artboard workflow. This target does not adopt independently sized Compositions, broaden SVG import, promise AI/PSD compatibility, or require a Symbols/linked-instance feature. A Japanese short-heading fixture with mixed Latin text, punctuation/parentheses, and a tate-chu-yoko case is a proposed coverage fixture for the already adopted Japanese/English text scope; its exact supported shaping rules must be made explicit before treating it as a release gate.

**Acceptance status:** adopted as the next representative P0 workflow by the user's instruction. **Implementation status:** the component capabilities are described in Desktop scope and migration records, with some shared command families already present. **Verification status:** the task-wide restart/re-edit, UI-versus-machine parity, mixed Japanese/Latin fixture, source-preserving Boolean Undo, and export checks have not been run as a single current-build scenario. Prior focused suite/build evidence is version-scoped and does not substitute for this acceptance run.

### Scoped implementation — Multi-input Boolean

- Implemented with ordered, stable input keys, closed-contour validation, editable Path output and the shared `connect` command path. A and B are required; Union/Intersect fold all inputs, Subtract removes the union of inputs after A, and Difference folds the existing symmetric-difference operation. Legacy A/B projects retain their parameter shape and schema version until an additional socket is used; expanded projects store `booleanInputOrder` under schema 40. See [architecture](architecture.md) and the focused Boolean tests.

#### P0 candidates (user-prioritized; design only)

- **Display units without geometry drift.** Offer mm, cm, px, in, and pt as view/input units over a stable canonical geometry representation. Use the CSS absolute-length baseline `1 in = 25.4 mm = 96 CSS px` and `1 pt = 1/72 in`; changing the displayed unit must not rewrite geometry, and rounding must affect presentation only. CSS defines these absolute-length equivalences. [W3C CSS Values and Units](https://www.w3.org/TR/css-values-3/#absolute-lengths)
- **Dimension-aware numeric expressions.** Accept entries such as `10cm`, `1in+5mm`, and `100mm/3`; convert compatible length terms to the canonical unit and reject incompatible dimensions or division by zero without changing the last committed value. Adobe documents unit-suffixed values and basic arithmetic in numeric fields as a useful interaction reference, not a parity requirement. [Adobe precise values](https://helpx.adobe.com/illustrator/desktop/get-started/learn-the-basics/enter-values-in-panels-and-dialog-boxes.html)
- **Separate artboard resize from artwork scaling.** Resizing an artboard changes only its output bounds; it keeps placed artwork and physical object sizes unchanged. Scaling artwork is a separate explicit action. Adobe exposes a distinct “Scale artwork with Artboard” action, which is a useful precedent for making the choice visible. [Adobe artboard scaling](https://helpx.adobe.com/illustrator/desktop/create-manage-artboards/add-edit-artboards/scale-artwork-with-artboard.html)
- **Explicit export scope with preview.** Provide Artboard, Selected items, Painted bounds, and Custom region scopes, with a preview of the exact crop. Painted bounds must include visible stroke and shadow extents when those effects are supported. Illustrator distinguishes artboard export from all/range choices; this proposal additionally calls for selection and painted/custom bounds. [Adobe export scopes](https://helpx.adobe.com/illustrator/using/exporting-artwork.html)
- **Exactly one PNG sizing mode at a time.** The Desktop route already offers mutually exclusive scale and physical-PPI modes and previews final integer pixel dimensions; exact-pixels mode remains a candidate. Keep document CSS-pixel size, physical size, raster pixel count, and PPI distinct. At the CSS 96 px/in baseline, a 100 x 50 mm artboard is 377.9527559055 x 188.9763779528 CSS px. At 300 PPI it rasterizes to about 1181 x 591 px; A4 (210 x 297 mm) at 300 PPI is about 2480 x 3508 px. A 100 mm width at 2x scale is about 756 px, while 100 mm at 300 PPI is about 1181 px: those are different modes, not interchangeable settings.
- **One cross-client export job and result contract.** Model an export request with a source snapshot/revision, targets and regions, ranges, one or more format variants, destination, naming template, preset, collision policy, and format-specific settings. Validate once and let UI and AI call the same typed command; this shared UI/AI command is a P0 design constraint. A separate CLI surface can follow later. Return the same per-artifact result report (path, target, format, final pixel/page dimensions, status, warnings, and fidelity/loss notes). Keep the native editable project as the source of truth; write exports as derived artifacts and never mutate the project as a side effect. Before a batch, preview target count, output variants, final dimensions, names, and collisions. On partial failure, report success, warning, and failure per output and allow retry of failures without rerunning successful outputs. This contract is a Nect design proposal, not a claim that any comparator has this exact abstraction.

#### P1/P2 candidates (design study only)

- **P1 - background, antialiasing, and PNG density.** Support transparent or a chosen background and an explicit antialiasing choice. If physical output density is requested, write and verify PNG `pHYs` as integer pixels per metre: 300 PPI corresponds to about 11811 px/m, which reads back as approximately 299.9994 PPI. The PNG specification defines `pHYs` in pixels per unit and a metre unit flag; density metadata alone does not add image detail or change the existing pixel samples. [W3C PNG pHYs](https://www.w3.org/TR/png-3/#11pHYs). Keep the physical-size-times-PPI rasterization mode distinct from a metadata-only density edit.
- **P1 - separate SVG output choices.** Fixed px/mm/cm root sizing, responsive `100%` sizing, and an optional 2–8 decimal geometry precision are now implemented on SVG export copies. `Default` retains legacy output bytes; explicit precision rounds geometry and selected numeric paint attributes while preserving the root physical dimensions and canonical pixel `viewBox`. A contour, image extent, stroke width, radial radius, or linear-gradient axis that would collapse to zero is rejected with guidance to choose more precision or Default. Text content, layer labels, IDs, colors, gradient URLs, and embedded image data are not numerically rewritten. Text editability versus outlining and linked-image output remain design-only choices. SVG import converts supported absolute root lengths to 96 CSS px/in; a 100 x 50 mm round-trip with a matching zero-origin viewBox is verified. Non-zero origins and root/viewBox scale mismatches remain unsupported, and their fail-closed behavior is covered by focused tests. [W3C SVG 2 viewBox](https://www.w3.org/TR/SVG2/coords.html#ViewBoxAttribute), [Adobe SVG options](https://helpx.adobe.com/illustrator/using/exporting-artwork.html#svg_export_options)
- **P2 - print/PDF output.** Physical page size, multi-page versus one-file-per-page delivery, PDF standard/version, compression/downsampling, bleed, printer marks, ICC profile handling, font subset/outline/editability policy, transparency/overprint, and RGB/CMYK conversion need separate requirements and validation. A displayed “CMYK” label or chosen page size does not by itself prove that a color conversion to an output profile occurred. [Adobe marks and bleeds](https://helpx.adobe.com/illustrator/using/printers-marks-bleeds.html), [Adobe PDF options](https://helpx.adobe.com/illustrator/using/pdf-options.html)

#### Acceptance probes before implementation is called complete

1. Toggle among mm/cm/px/in/pt repeatedly, save, reopen, and compare canonical values; there must be no accumulated drift. Evaluate supported mixed-unit expressions and verify an incompatible expression or divide-by-zero leaves the committed value unchanged.
2. Resize an artboard from 100 mm to 200 mm while a 10 mm object remains physically 10 mm; invoke the separate artwork-scale action and verify it becomes 20 mm.
3. Inspect PNG IHDR dimensions and pHYs values independently. Confirm final integer dimensions for all three sizing modes, verify a metadata-only density edit leaves IHDR unchanged, and verify device-pixel-ratio does not alter exported pixel dimensions.
4. Round-trip SVG through varied `viewBox` origins and scales; inspect fixed/responsive width/height, text editability/outline behavior, and embedded/linked image choices separately.
5. Verify artboard/selection/painted/custom scopes against previews, including stroke and shadow bounds where supported. Confirm transparent, white, and chosen-color backgrounds produce distinct expected pixels.
6. Run one job with multiple targets, formats, and scale variants. Check destination, naming, collision handling, final dimensions, per-file statuses, and the no-silent-partial-failure report.
7. Submit the same supported export request through ordinary UI and the AI command. Confirm both validate the same snapshot/settings, create equivalent outputs and reports, and leave the native editable project unchanged.
8. For PDF, separately verify one multi-page result versus one file per selected page/artboard, intended physical page size, bleed/marks, font policy, transparency, and color profile/conversion behavior against a defined print fixture.

**Status:** these are user-prioritized design candidates, not blanket acceptance of the whole export roadmap. Fixed/responsive SVG root sizing, SVG geometry precision, and PNG PPI metadata have scoped implementations recorded in `desktop/docs/verification.md`. Shared export-job contracts, export targets/batches, alternate text and linked-image modes, background/antialiasing, print/PDF, and transform-preserving round-trips for non-zero origins or mismatched root/viewBox scales remain unsupported; the importer now rejects those cases rather than silently changing size or position. AI access to a shared export command/result remains a P0 design constraint; a separate CLI is optional later work. Independent Composition sizing remains P1 study; Symbols remain Deferred; the active checkpoint and legacy Qt mission/format boundaries are unchanged.

## Traceability conclusion

For planning, treat the current Desktop Must list plus the explicitly adopted P0 goals above as the acceptance scope; trace individual legacy requirements into it only when the Brief or a current decision explicitly does so. Keep “legacy feature exists,” “similar feature exists in Desktop,” “format compatible,” and “same semantics verified” as separate claims. The present evidence supports selective adoption and deliberate exclusions, but **not full carryover or full Illustrator-replacement completion**.
