# Nect legacy → Desktop requirements crosswalk (bounded first pass)

## Bottom line

The available evidence does **not** support saying that all old Nect requirements were carried over. The 2026-10-16 Desktop Brief selects a practical offline Windows editor and a named set of Musts, while explicitly preserving the C++/Qt Mission and keeping the legacy and Desktop formats distinct. The legacy product-direction document also cautions that its accepted direction does not pull the whole roadmap into a milestone. This is a bounded traceability pass over major requirement areas, not a full audit of every Notion requirement or every implementation/test.

Status labels here describe the current Desktop scope, not the maturity of the old app:

- **verified implemented**: source records a named verification for the relevant behavior/build; scope and tested version still apply.
- **implementation present, not validated**: code/spec describes the behavior, but the exact current WIP or required real environment has not been fully accepted.
- **deferred**: not a current Must; separate future work/decision.
- **non-goal**: explicitly outside the current boundary.
- **unknown**: available sources do not establish an answer or measurable criterion.
- **needs user decision**: a product-level ambiguity remains if someone wants to claim that broader outcome.

## Material source inconsistencies / missing inputs

1. **Requirement authority:** the old Git `docs/product-direction.md` explicitly says it is an extract, not the complete Notion requirements database. The actual requirement database/leaf pages were not mapped in this pass. The product-home's redesign note is marked `unverified` and records open questions. Therefore this cannot certify complete requirements coverage.
2. **Provided Notion link mismatch:** the URL named as a “brief” in the handoff is an operations-design page. The README's linked product home is relevant context, but does not replace the adopted Desktop `CURRENT_GOAL.md`.
3. **Product spec staleness/conflict:** Desktop product spec §9 says native WebView2/dialog/save-close acceptance is incomplete, while `desktop/docs/document-lifecycle.md` later records actual native dialog, close, save and cold-reopen results on specified executables. Treat these as version-scoped evidence; update/reconcile the status summary before claiming current-WIP native completion.
4. **Gradients:** product-spec sections conflict as noted above; no single status should be inferred without fresh code/test readback.
5. **Missing design artifacts:** the adopted `task-16/astra/brief-r0.md` and `architecture-addendum.md` are named by hash in `CURRENT_GOAL.md` but are not present in this selected workspace snapshot. The Brief summary is available in `CURRENT_GOAL.md`; original documents were not independently reviewed here.
6. **No all-tests audit:** this pass did not run tests or inspect every feature/test. It crosswalks documented requirements/status only. Current WIP validation boundaries come from `CURRENT_GOAL.md` and do not amount to an implementation review.

## Traceability conclusion

For planning, treat the current Desktop Must list as the adopted acceptance scope; trace individual legacy requirements into it only when the Brief or a current decision explicitly does so. Keep “legacy feature exists,” “similar feature exists in Desktop,” “format compatible,” and “same semantics verified” as separate claims. The present evidence supports selective adoption and deliberate exclusions, but **not full carryover or full Illustrator-replacement completion**.
