# Composition session owner

CompositionSessionOwner owns the full multi-Composition project snapshot and chronological project History. It projects the active Composition into the existing CommandSession for core command validation, then maps every committed edit back into that Composition while retaining the other Composition records and project-shared font/image assets.

Undo and Redo traverse project History, including edits made in different Compositions. Composition switching does not add a history entry or change the project revision. Create, rename, resize and delete operations are single project-history steps. The owner exposes a stable History facade whose doc, past and future values are legacy Document projections for the active Composition; this keeps existing selection-history bookkeeping attached to stable snapshots. Opaque per-entry tokens let the UI preserve the current selection across a project-only rename, even when Undo runs in another Composition. Tokens are local to the project owner and never saved. Prepared commands and variable-aware Undo/Redo use the existing document-preparation bridge before committing project History.

main.js now creates this owner at startup and routes command dispatch, Undo/Redo, New, native and browser Open, Save, recovery, and window.nect.load through the project envelope. Old single-Document JSON is passed through the core deserializer/upgrader before migration. SVG and PNG export use the active Composition's Document projection and dimensions. The UI exposes Add Composition, Project → Rename composition, and a horizontal header tablist when multiple Compositions exist. Left/Right and Home/End move focus; Enter/Space and click activate; F2 renames the focused tab. Rename uses a stable Composition ID and the same typed owner command exposed by `window.nect.dispatch`, with captured Session and project revisions. It is one project History step; cancellation, a no-op or stale dialog preserves History and Redo. Long names truncate visually and remain available in the accessible name and title; the tablist scrolls horizontally. Switching saves and restores window-local active Layer, node/artwork/point selection, selected Guide, Canvas zoom/fit/pan, graph zoom/scroll, tool, and viewer bindings by stable Composition ID. Restored IDs are filtered against the target Composition. The state is not serialized; Open/New/recovery clear it.

The existing Composition Reference remains a reference to a Layer node graph within the same outer Composition; it does not render another outer Composition. Separately, supported typed expressions can read properties across Compositions under the versioned [parameter reference contract](parameter-reference-expressions.md). The additive project Import action selects any nonempty source Composition set (all selected by default), retaining source order and dimensions, ordered Layers, required shared assets and Layer-graph references. The dialog uses the model's project capacity to keep oversized selections visible but unavailable until adjusted. The validated batch is committed as one project-history operation; Open remains replacement. Changes to the active Session or project while the source is being selected reject the stale import.

The owner orchestration tests inject small History and Session doubles. The focused model/import/owner/view-state/action-contract run passes 33 tests, including legacy core-upgrader routing, project-wide Undo/Redo, complete Composition-set import, per-Composition state isolation, stale-ID filtering, and project-replacement reset. An app-level DOM fixture additionally exercises the production core factory through Save/Open/recovery/public-load and multi-Composition tab switching. Sandboxed Chrome also covers selected multi-Composition import, one linked palette, Undo/Redo, stale-selection rejection and a browser save/reopen; wider native WebView acceptance remains separate.
